## 2. 経緯の概要

### 何が起きたか
1. サイト（daisukeminowa.com）は Next.js（表示）と Strapi Cloud（データと写真の管理）で動いていました。
2. Strapi Cloud が無料プランを廃止し、プロジェクトのデータが削除されました。
3. 本番のサイトは、約90日前にビルドされたページのまま文章だけが表示され、**写真はすべて表示されなくなりました**。

### 何を救えたか；
- 本番のページの HTML から、作品22点・展示歴8件・学歴2件の文章を救出し、`rescue/` に保存しました。
- **作品の写真22枚は救出できませんでした**（Strapi Cloud のストレージが消え、Vercel のキャッシュにも Web アーカイブにも残っていなかった）。
- 元の写真のファイル名は `rescue/image-checklist.csv` にまとめてあります。お父さんの手元の写真を探すときに使います。

### 検討した方法
| 候補 | 内容 | 選ばなかった理由 |
|-|-|-|
| microCMS | 国産の CMS サービス（無料プランあり） | 外部サービスの無料プランに頼るため、Strapi Cloud と同じことが起き得る |
| Sanity | 海外の CMS サービス（無料プランあり） | 同上 |
| Strapi を Lightsail で運用 | 今のコードのまま自分のサーバーで動かす | 月額がかかり、サーバーの保守も必要 |
| AWS で一から自作 | 管理画面も含めて自作する | 作る手間と保守が大きい |
| ファイル方式 | データを JSON で GitHub に置き、管理画面を自作または Decap CMS | 管理画面の自作は前例が少なく、うまく動くか不安が残る |
| **Payload CMS（採用）** | Next.js の中に組み込むオープンソースの CMS | 下の「選んだ理由」を参照 |

### 優先したこと（順番）
1. 有料のプランを使わない
2. 外部サービスへの依存を減らし、乗り換えられるようにする
3. お父さん（技術に詳しくない）が使いやすい
4. 実績のある設計にする（自作の部分を減らす）
5. Next.js から別のフレームワークに移らない（Vercel の仕組みで済ませる）

### Payload を選んだ理由
- Next.js の中で動くライブラリで、外部のサービスではない（MIT ライセンス）
- 管理画面・ログイン・写真の自動縮小・下書きと公開・型の生成が、最初から付いている
- DB（Postgres）と写真の保存先（Vercel Blob）は、Vercel の管理画面から用意でき、どちらも標準の技術なので乗り換えられる

## 3. 今の構成

### 前の構成
```
お父さん ──▶ Strapi の管理画面 ─┐
                               ├─ Strapi Cloud（データと写真）  ← 有料化され、データが消えた
閲覧者 ──▶ Next.js（Vercel）───┘   ビルドのときに HTTP で取得
```

### 今の構成
```
                        Vercel
                  ┌───────────────────────────────┐
お父さん ──────────▶│ Next.js                        │
 （管理画面）        │  ├─ 公開ページ（静的に作る）      │──▶ Neon（Postgres）  文章のデータ
                  │  └─ Payload（/admin、/api）      │      本番用とプレビュー用で別々
閲覧者 ────────────▶│                               │
                  └───────────────────────────────┘
       写真はブラウザから直接 ─────────────────────────▶ Vercel Blob  写真
                                                          本番用とプレビュー・開発用で別々
```

### 主な部品
| 部品 | 役割 | 補足 |
|-|-|-|
| Next.js 15.3.9 | サイト全体 | Payload の対応範囲に合わせて固定（15.3.9 以上 15.4 未満） |
| Payload 3.92.0 | 管理画面、データの読み書き、ログイン | 日本語と英語に対応 |
| Neon（Postgres） | 文章のデータ | Vercel Marketplace から作成。`DATABASE_URL` |
| Vercel Blob | 写真 | ブラウザから直接アップロード（4.5MB の上限を回避） |
| sharp | 写真の縮小 | 表示用（4000px 以内、画質90）とぼかし用（32px） |

### コレクション
| コレクション | 内容 | 下書き |
|-|-|-|
| 作品（artworks） | タイトル・写真・縦横（cm）・技法・制作日・説明 | あり |
| 展示歴（exhibition-entries） | 展示名・開始日・終了日・場所・メモ | あり |
| 学歴（education-entries） | 学校名・入学年・卒業年・メモ | あり |
| 写真（media） | 写真のファイル | — |
| ユーザー（users） | 管理者と編集者 | — |

### 権限
- **管理者**：すべての操作ができる
- **編集者（お父さん用）**：作品・展示歴・学歴・写真の追加・編集・公開・削除ができる。ユーザーの管理はできない（メニューにも出ない）
- 作品で使われている写真は、削除できない（消すと作品が「公開中なのに写真がない」状態になるのを防ぐため）

### 環境
| 環境 | DB | 写真 |
|-|-|-|
| 本番 | Neon（本番用） | Blob（本番用） |
| プレビュー | Neon（プレビュー用） | Blob（プレビュー・開発用） |
| 手元の開発 | Docker の Postgres（`client/docker-compose.yml`） | Blob（プレビュー・開発用） |

プレビューの URL は、Vercel にログインした人しか見られません（Deployment Protection）。

### デプロイとマイグレーション
- Vercel のビルドでは `npm run ci`（`payload migrate && next build`）を実行します（`client/vercel.json`）。
- DB の変更は、マイグレーションのファイル（`client/src/migrations/`）で管理します。
- 手元の開発では、Payload がテーブルを自動で作り直すので、`migrate` は使いません。設定を変えたら `npx payload migrate:create` でマイグレーションを作ります。

### スクリプト
| ファイル | 用途 |
|-|-|
| `client/scripts/seed.ts` | `rescue/` のデータを DB に入れる（データがあれば何もしない） |
| `client/scripts/create-admin.ts` | 管理者を作る（環境ごとに一度だけ） |

## 4. 作業で学んだ注意点

- **Neon（本番・プレビュー）に向けてスクリプトを実行するときは、必ず `NODE_ENV=production` を付ける。** 付けないと、Payload がテーブルの自動作り直しを行い、`payload_migrations` に `dev`（batch -1）の行を書き込みます。この行があると、デプロイ時の `migrate` が何もせずに終わってしまいます。
- **接続先は、手元の秘密のファイル（`.env.*.local`、Git の対象外）から読み込む。** `vercel env run` は、このプロジェクトでは環境変数が正しく渡らず、誤ってデプロイが作られたことがあるので使わない。
- **Next.js の外から seed したあとは、ページが自動で作り直されない。** 再デプロイするか、管理画面で何か1つ保存する。
- **開発サーバー（`npm run dev`）が動いている間は、`npm run build` を実行しない。** 同じ `.next/` を使うため、開発サーバーが壊れる。
- Blob アダプタの `addRandomSuffix` は、このバージョンでは URL と実際のファイル名がずれるので使わない。
